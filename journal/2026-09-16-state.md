# Runtime State

## Why State is the execution field

State is the mutable execution context shared by LangGraph nodes during one
graph run or thread. It is not a service, repository, runtime dependency
container, or place to store configuration.

## The first frozen contract

`messages` is the only State field with a currently exercised, stable contract.
It contains LangChain messages for the current execution. Entry contributes a
`HumanMessage`; later Agent and tool boundaries may contribute `AIMessage` and
`ToolMessage`.

Nodes return updates and LangGraph's `add_messages` reducer merges them. This
replaces the old handwritten ReAct pattern of mutating or appending to a shared
messages list: the node says what changed, and the graph owns the merge.

## Deliberately deferred fields

`task` is still a future placeholder; no task is inferred from a message.
`artifacts` and `pending_action` remain future output and approval concepts.
`status` and `route` are retained because the safe scaffold currently uses them,
but their long-term semantics are not frozen. They are not reasons to make
those fields mandatory for Entry.

## State versus RuntimeContext

State carries execution-specific mutable data. RuntimeContext carries process
dependencies such as paths, registries, model slots, and persistence slots.
Credentials, raw configuration, clients, and workspace paths must not enter
State; messages and current actions must not enter RuntimeContext.

## Open questions

- Which message lifecycle should the real Agent node own?
- Does `status` duplicate Task status once task execution is designed?
- Is `route` only a transitional scaffold field, or is explicit routing state
  needed for a later checkpoint/resume contract?
