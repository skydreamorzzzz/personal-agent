# Entry Boundary

## Why Entry is separate

Entry is the boundary between external adapters and the already-composed
runtime. Keeping it separate prevents CLI or future web/mobile adapters from
owning reasoning, prompts, tools, memory, configuration, or dependency setup.

## Frozen contracts

User-authored text becomes `UserMessageInput` and then one LangChain
`HumanMessage`. The original content is not rewritten. Entry does not create a
system, assistant, or tool message.

Background notifications use `BackgroundEventInput` with structured payload.
They are not fabricated as user speech because no user authored them. Their
Task/State integration remains open.

Human responses to a paused graph are a third channel. Resume is not a new
message and will later use LangGraph interrupt/resume semantics; this round does
not implement it.

## Current reality

The CLI can submit one message to the safe graph. Web and mobile have only
normalization helpers, not servers or applications. Background events can be
validated but are not invoked. The graph still has no real LLM or side effects.

## Open questions

- How should a background event create or attach to a Task and thread?
- Which entry metadata belongs in RuntimeContext versus task state?
- What checkpoint/thread contract should a future resume adapter require?
